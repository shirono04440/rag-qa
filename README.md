# MemoTodo 文档问答 · 检索增强（RAG）实现

一个**零第三方依赖**的检索增强问答系统：给自己的项目代码和文档建索引，用中文提问，返回带原文出处的答案。

- 语料：22 个文件、228 个语义块
- 检索：10 条人工标注问题上 **Hit@1 = 0.90，Hit@3 = 1.00，MRR = 0.933**
- 速度：单次检索 **0.46 ms**（纯 Python，无模型加载）
- 依赖：只用到 Python 标准库，`python app.py` 即可跑

## 为什么不用 LangChain / 向量数据库

这是刻意的取舍。常见做法是 `sentence-transformers + Chroma`，但那样：

1. 装 torch 要 2GB，模型还要另下 400MB，换台机器就废
2. 向量只能做语义匹配，**专有名词和代码标识符（`SetWindowRgn`、`WAL`）经常召不回**
3. 出了问题只能黑盒调参，说不清为什么召回失败

所以这里手写了 **BM25 + TF-IDF 余弦的混合检索**，中文按 `uni-gram + bi-gram` 切分。代码量的代价换来三件事：可解释、可离线、可复现。

## 架构

```
rag-qa/
├── app.py              # Web 界面（http.server，标准库）
├── eval.py             # 评测：Hit@1 / Hit@3 / MRR
├── rag/
│   ├── corpus.py       # 语料加载（md / py / txt / json）
│   ├── chunker.py      # 切块 + 中文分词（uni/bi-gram）
│   ├── index.py        # BM25 + TF-IDF 倒排索引，可落盘 JSON
│   ├── answer.py       # 检索 →（可选）大模型 → 摘录式兜底
│   └── llm.py          # 可选：接入 OpenAI 风格接口
├── tests/test_all.py   # 自测
└── data/index.json     # 建好的索引
```

数据流：

```
文档 → 切块（420 字 / 80 字重叠） → 分词 → 倒排索引
                                          ↓
提问 → 分词 → BM25 打分 ┐
                        ├→ 归一化加权融合 → Top-K → 答案 + 出处
提问 → 分词 → TF-IDF 余弦 ┘
```

## 快速开始

```bash
# 1. 建索引（换成你自己的目录）
python -m rag.build --source D:\todo --out data/index.json

# 2. 命令行提问
python -m rag.cli "今日完成是怎么判断的"

# 3. Web 界面
python app.py   # 打开 http://127.0.0.1:8000

# 4. 评测
python eval.py
```

## 检索效果

10 条问题覆盖功能、实现、打包、测试四类，标注了期望命中的文件：

| 指标 | 数值 | 含义 |
|---|---|---|
| Hit@1 | **0.90** | 第一名就是正确文件的比例 |
| Hit@3 | **1.00** | 前三名包含正确文件的比例 |
| MRR | **0.933** | 正确结果平均排在第 1.07 位 |
| 平均检索耗时 | 0.46 ms | 228 块、3151 词表 |

复现：`python eval.py -v` 可看到每一题的排名与召回的 Top-3 文件。

## 答案是怎么来的

两段式，**先保证不编造**：

1. **有 `DEEPSEEK_API_KEY`** → 把 Top-5 片段拼成上下文，让模型只依据资料回答
2. **没有 key** → 摘录式兜底：从命中块里挑与问题词重合度最高的 3 句，过滤代码行后拼接

两种模式都会返回引用（`文件:行号`），方便点回去核对原文。这也是 RAG 相对纯大模型的价值所在——**答案可追溯**。

## 已知不足

- 只做词面匹配，同义改写（"开机启动" vs "自启动"）会漏召回，加一层同义词表或向量召回能补
- 摘录式答案是把句子拼起来，读起来不如生成式通顺
- 切块按字符数硬切，遇到长函数会被切断；按语法结构切会更合理
